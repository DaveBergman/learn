# 3.0 Correlating Events — Transactions (15%)

## 3.1 Identify transactions

A **transaction** is a group of events related by a common field value across a
time window. The `transaction` command automatically groups related events into
logical units, making it ideal for tracking sequences of actions from the same
user, session, or request.

Key characteristics:
- Transactions are **event-level groupings** — each event remains discrete
  within the transaction, with added metadata.
- Transactions have metadata fields: `transaction_duration`, `transaction_src`,
  and a host of others depending on what fields share values.
- Use transactions to track sequences: login → click → purchase → logout.
- Unlike `stats`, which collapses groups into single rows, `transaction` leaves
  events intact but marks them with a shared transaction ID.

Source: [`transaction` command reference](https://docs.splunk.com/Documentation/Splunk/latest/SearchReference/Transaction) — Splunk Enterprise/Cloud Platform docs, latest version. Accessed 2026-07-19.

## 3.2 Group events using fields

The `transaction` command's **primary grouping mechanism** is field value
matching. All events with identical values in the specified field(s) within a
time window belong to the same transaction.

Example:
```
sourcetype=web status=200
| transaction sessionID
```

This groups all events with the same `sessionID` into a transaction. If no time
constraint is specified, `transaction` uses the default `maxspan=infinite` (no
time limit) and `maxpause=30m` (events separated by more than 30 minutes start
a new transaction).

Fields specified in `transaction` are the **only** ones used for grouping;
multiple fields require all to match for events to be in the same transaction.

Source: [`transaction` command reference](https://docs.splunk.com/Documentation/Splunk/latest/SearchReference/Transaction) — Accessed 2026-07-19.

## 3.3 Group events using fields and time

Time-based constraints on transactions are controlled by two options:

- **`maxspan`** — the maximum time span for a transaction. Events separated by
  more than `maxspan` will be in different transactions (even if they share the
  grouping field value).
- **`maxpause`** — the maximum duration of inactivity (time gap between
  consecutive events). If two consecutive events are separated by more than
  `maxpause`, a new transaction starts.

Example:
```
sourcetype=web
| transaction sessionID maxspan=1h maxpause=10m
```

This groups events with the same `sessionID`, but:
- Events more than 1 hour apart belong to different transactions.
- If there's a 10+ minute gap between events, a new transaction starts.

Both options default to `infinite` (no limit) if unspecified, except `maxpause`
which defaults to `30m`.

Source: [`transaction` command reference](https://docs.splunk.com/Documentation/Splunk/latest/SearchReference/Transaction) — Accessed 2026-07-19.

## 3.4 Search with transactions

Once transactions are created, you can search and filter on transaction-level
fields and properties:

- **`transaction_duration`** — the time span of the transaction (end time minus
  start time).
- **`eventcount`** — number of events in the transaction.
- **`linecount`** — total number of lines across all events in the
  transaction.

You can filter on these using `search` or `where`:
```
sourcetype=web
| transaction sessionID maxspan=1h
| search transaction_duration > 300
```

This returns only transactions longer than 5 minutes (300 seconds).

You can also use Boolean operators within a transaction context:
- `transaction ... startswith=startEvent endswith=endEvent` — groups events
  from a `startEvent` to the next matching `endEvent`.

Source: [`transaction` command reference](https://docs.splunk.com/Documentation/Splunk/latest/SearchReference/Transaction) — Accessed 2026-07-19.

## 3.5 Report on transactions

Once transactions are created, you can apply reporting and statistical commands
to them:

```
sourcetype=web
| transaction sessionID
| stats count, avg(transaction_duration) by eventcount
```

This counts transactions and averages their duration, grouped by the number of
events per transaction.

You can also pipe transactions into `timechart`, `chart`, or `table` for
visualization. Transactions preserve all original event fields, so you can
access any field from the original events within the transaction context.

Source: [`transaction` command reference](https://docs.splunk.com/Documentation/Splunk/latest/SearchReference/Transaction) — Accessed 2026-07-19.

## 3.6 Determine when to use transactions vs. stats

**Use `transaction` when:**
- You need to **preserve individual events** within a group.
- You want to track **temporal sequences** (e.g., login → action → logout).
- You need **original field values** from each event in the group.
- The grouping is based on **a common field value** shared across events.

**Use `stats` when:**
- You want **aggregate results** (one row per group).
- You're computing summaries: count, sum, avg, min, max, etc.
- You want **efficiency** — `stats` is faster than `transaction` because it
  doesn't preserve raw events.
- You don't need the original events themselves, only the aggregations.

**Key difference:**
- `transaction` creates a "virtual" group that still contains all original
  events; you can drill into each event.
- `stats` collapses the group into a single summary row.

Both can group by multiple fields; both support time-based constraints. Choose
based on whether you need the individual events or just summaries.

Source: Splunk Enterprise/Cloud Platform Search Reference — best practices comparison across `transaction` and `stats` command documentation, accessed 2026-07-19.
