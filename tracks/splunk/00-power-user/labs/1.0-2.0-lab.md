# Lab — Transforming, Filtering & Formatting (sections 1.0–2.0)

Runs against the live `splunk-am06` instance, `index=_internal
sourcetype=splunkd` — Splunk's own internal log data, always present on any
Splunk instance, so this lab works regardless of which of Dave's other
indexes have data at the time. Data confirmed live 2026-07-18 (sample event
fields: `_time`, `host`, `source`, `sourcetype`, and log lines carrying a
standard severity token — `WARN`, `INFO`, `ERROR` — as the first word after
the timestamp; Splunk's default `splunkd` sourcetype knowledge bundle
extracts this as the field `log_level` and the subsystem name as
`component`. If a task below doesn't return `log_level`/`component` as
expected, treat that as new information — check with `| fieldsummary` before
assuming the note above was wrong — the local knowledge bundle version may
differ.).

**Prerequisite check:** before starting, run `splunk_list_indexes` (confirm
`_internal` has events) — if `splunk-am06` is unreachable, check
`mcp__am06-ops__splunk_status` and tell Dave plainly rather than
proceeding.

## Task 1 (drills 1.1, 1.2 — chart vs timechart)

Scenario: you want to know, for the last 24 hours, how log volume is
trending over time, broken out by severity.

1. Write a `timechart` query counting `_internal`/`splunkd` events by
   `log_level`, in reasonable time buckets.
2. Then write a `chart` query showing total count by `log_level` only (no
   time dimension) — a single-table breakdown, not a time series.
3. Explain out loud (Feynman check) why task 1 needed `timechart` and task 2
   needed `chart`, not the reverse.

`answer_check`: task 1's query must include `timechart` with `by log_level`
(or an explicit `span`/`bins`); task 2's query must include `chart ... by
log_level` with **no** time-based field in the `BY` clause. Both should run
without error against real data and return non-empty tables.

## Task 2 (drills 2.1 — eval)

Scenario: you want a new field that labels each event as `"noisy"` if its
raw message is longer than 200 characters, else `"normal"`.

1. Write an `eval` expression creating a field `msg_size` using `case()` (or
   equivalent) based on the length of `_raw`.
2. Confirm the result isn't a Boolean field (per the note's constraint) —
   explain what you'd have gotten if you'd tried `eval msg_size = len(_raw)
   > 200` instead, and why that violates the eval-result rule from the note.

`answer_check`: query runs, returns a `msg_size` field with values
`"noisy"`/`"normal"` (or similar labels) — not `true`/`false`.

## Task 3 (drills 2.2 — search vs where)

Scenario: after running task 2's query, you want to keep only the "noisy"
events, using the field you just created.

1. Do this filter with `where`. Explain why `where` is the right tool here
   rather than `search` (hint: the field being filtered didn't exist before
   `eval` ran this pipeline).

`answer_check`: query pipeline is `... | eval ... | where msg_size="noisy"`
(or equivalent) — filtering on a derived field, correctly placed after the
`eval` that creates it.

## Task 4 (drills 2.3 — fillnull)

Scenario: `component` isn't populated on every internal log line.

1. Run a `stats count by component` and note whether any row shows a blank/
   `(null)` bucket to confirm nulls actually exist in this data before
   "fixing" them.
2. If nulls exist, add `fillnull value="unknown" component` to replace just
   that field's nulls with `"unknown"` — not all fields.

`answer_check`: if step 1 found nulls, step 2's query includes `fillnull
value=<something> component` (field list present, not a blanket fillnull);
if step 1 found no nulls, note that plainly rather than forcing a fillnull
onto data that doesn't need it.

## Grading

Each task is pass/fail against `answer_check` plus the Feynman explanation —
a syntactically correct query that Dave can't explain the "why" for isn't a
full pass per METHOD.md's Feynman-check principle. Log per-task results back
