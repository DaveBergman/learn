# 10.0 Using the Common Information Model (CIM) Add-On (10%)

## 10.1 Describe the Splunk CIM

The **Common Information Model (CIM)** is a **standard set of field names and
data structures** provided by Splunk to normalize diverse log sources. The CIM
add-on ensures that logs from different vendors (Windows, Linux, firewalls,
proxies, etc.) use consistent field names.

**Key characteristics:**
- **Standardization:** Different vendors use different field names; CIM defines
  a common vocabulary.
- **Add-on:** Installed as a Splunk add-on (TA-common_information_model or
  similar).
- **Supplements existing data:** CIM field mappings are applied via field
  aliases and calculated fields — your indexed data remains unchanged.
- **Enables cross-source analysis:** Once CIM is applied, you can write searches
  that work across all data sources.

**Example CIM normalization:**
Different sources use different names for the source IP:
- Windows: `src_ip`
- Cisco ASA: `source`
- Palo Alto: `source_address`
- Apache: `clientip`

**With CIM:** All map to a standard `src` field. Searches using `src` work across
all sources.

**CIM coverage areas (domains):**
- **Authentication** — logins, logouts, authorization events.
- **Network** — traffic, connections, DNS, proxies.
- **Intrusion Detection** — IDS/IPS alerts.
- **Vulnerability** — scanning, patching.
- **Web** — HTTP requests, responses, user sessions.
- **Email** — message logs, filtering.
- **Endpoint** — process execution, file changes.
- **And many others** — spanning security, infrastructure, and application logs.

Source: [Common Information Model (CIM) documentation](https://docs.splunk.com/Documentation/CIM/latest/User/Overview) — Splunk Enterprise/Cloud Platform docs. Accessed 2026-07-19.

## 10.2 List the knowledge objects included with the Splunk CIM Add-On

The CIM add-on includes several types of **knowledge objects** (pre-built
configurations that normalize data):

### 1. **Field Aliases**
Map vendor-specific field names to CIM standard names.
- **Example:** `src_ip` (Windows) → `src` (CIM standard).

### 2. **Calculated Fields**
Derive new fields from existing data to match CIM standards.
- **Example:** Extract the domain from a user email and store in the `user` field.

### 3. **Event Types**
Pre-defined event types for common log patterns.
- **Example:** `authentication:success`, `network:traffic`, `web:access`.

### 4. **Tags**
Tags applied to CIM-compliant events for easy filtering.
- **Example:** Tag with `network` for network events, `security` for security
  events.

### 5. **Data Model Definitions**
CIM provides several pre-built data models that leverage the normalized fields.
- **Example:** "Authentication" data model with fields like `user`, `src`,
  `authentication_method`.

### 6. **Correlation Searches** (in some versions)
Saved searches designed to detect common threat patterns using CIM-normalized
data.

**CIM add-on structure:**
- Located in `$SPLUNK_HOME/etc/apps/TA-common_information_model/`.
- Includes `props.conf` (field aliases, calculated fields), `tags.conf`,
  `eventtypes.conf`, and data model definitions.

**Accessing CIM objects:**
- **Settings → Data Models** — view pre-built data models.
- **Settings → Tags** — see CIM tags.
- **Settings → Field Extractions** — inspect field aliases and calculated
  fields.

Source: [CIM Add-On documentation](https://docs.splunk.com/Documentation/CIM/latest/User/Overview) — Accessed 2026-07-19.

## 10.3 Use the CIM Add-On to normalize data

To use CIM and normalize your data:

### Step 1: Install the CIM Add-On
1. Download from Splunkbase or install via your package management.
2. Restart Splunk.
3. Verify installation: **Settings → Installed Apps** → look for "Common
   Information Model".

### Step 2: Identify relevant data sources
Determine which data sources (Windows logs, network traffic, web access logs,
etc.) should be normalized.

### Step 3: Apply CIM via props.conf
CIM is applied automatically via field aliases defined in `props.conf`. Once
installed, any data matching CIM-mapped sourcetypes automatically gets CIM
fields.

**Example:** When you index Windows security logs (`sourcetype=WinEventLog:Security`),
CIM aliases automatically create standard fields like `src`, `dest`, `user`,
`action` based on Windows-native fields.

### Step 4: Use CIM fields in searches
Write searches using CIM standard field names:
```
src=192.168.1.100 action=success tag=authentication
```

This search works across Windows, Linux, Cisco, Palo Alto, and any other source
with CIM mappings, without rewriting the search for each source.

### Step 5: Leverage CIM data models and pivots
Open a CIM data model in pivot:
1. **Pivot → Create Pivot → select a CIM data model** (e.g., "Authentication").
2. Build your report using CIM-normalized fields.
3. Pivot queries are much simpler because all fields use consistent names.

**CIM benefits in practice:**
- **Cross-source dashboards** — one dashboard works with data from multiple
  vendors.
- **Reusable searches** — write a search once, use it across different sources.
- **Faster investigations** — search for `user`, `src`, `dest` without learning
  vendor-specific field names.
- **Compliance and audit** — standardized fields simplify compliance reporting.

**Customizing CIM:**
If a source isn't covered by default CIM mappings, you can extend CIM:
1. Create custom field aliases or calculated fields in your app's
   `props.conf`.
2. Tag events with appropriate CIM tags.
3. Add custom event types aligned with CIM domains.

**Best practices:**
- Review CIM documentation for your data sources.
- Use CIM-compliant field names in dashboards and reports.
- Contribute new mappings if your vendor isn't covered.
- Document any custom extensions to CIM.
